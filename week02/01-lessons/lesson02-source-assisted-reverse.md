# Lesson 02：源码辅助逆向，不做顺序读代码

建议用时：90 分钟。

## 1. 本周为什么先保留源码

直接把源码全部拿掉，看起来更像逆向，但初学阶段容易把时间耗在符号、工具和构建差异上。本周保留源码，是为了训练三个可迁移能力：

1. 从业务问题选择分析入口。
2. 把数据生产者、转换者、消费者连成图。
3. 用 LLDB 验证真实执行路径，而不是相信静态猜测。

第 3 周会把这些方法迁移到 Mach-O 和反汇编。源码辅助阶段若仍只会逐文件阅读，拿掉源码后会立刻失去方向。

## 2. 五种入口

### 行为入口

从可观察行为开始：按钮点击、错误提示、网络请求、文件生成、页面跳转、崩溃。

本周 Demo 的行为入口是三个场景输出。先记录输入、结果和差异，再定位实现。

### 数据入口

从敏感数据或安全字段开始：token、ownerID、role、premium、签名、设备 ID。

追踪时问：谁写入、谁读取、是否复制、在哪里失效、最终影响什么。

### API 入口

从高价值 API 开始：Keychain、网络发送、文件写入、WebView bridge、密码学、反调试 API。

API 入口适合陌生 App 侦察，但一个 API 命中只是线索，必须回溯调用者与业务上下文。

### 控制流入口

从 `authorize`、`validate`、`canAccess`、`isPremium`、`verify` 等判断点开始，再向上找调用者、向下找消费点。

安全命名未必存在，混淆后也可能消失，因此不能只依赖关键词。

### 边界入口

从跨层边界开始：UI -> service、App -> SDK、Swift -> ObjC、Java -> JNI、客户端 -> API。

边界处通常发生数据转换、权限委托或错误信任，是高价值观察点。

## 3. 用“生产、转换、消费”代替全文阅读

对每个关键值做 PTC 分析：

```text
Producer：值在哪里产生？
Transformer：值在哪里复制、编码、映射或组合？
Consumer：哪个判断或敏感操作最终使用它？
```

以 `requestedOwnerID` 为例：

- Producer：场景入口传入 `"alice"`。
- Transformer：`ExportRequestFactory` 将其写入请求对象。
- Consumer：安全服务端与 token 对应用户比较；错误服务端完全忽略它。

忽略字段也是证据。授权代码收到 owner 却没有比较，是比“客户端可以改 owner”更接近根因的发现。

## 4. 构建候选调用图

第一遍只画候选，不要求完全正确：

```text
LabScenarioRunner.run
  -> MockIdentityService.signIn
  -> MemorySessionStore.save / overwriteCachedClaimsForLab
  -> SensitiveActionCoordinator.exportReport
  -> ClientPolicyEvaluator.evaluate
  -> ExportRequestFactory.makeRequest
  -> MockExportAPI.perform
  -> authorizeSecurely / authorizeUsingClientClaims
```

随后为每条边标记证据等级：

- S1：仅从命名猜测。
- S2：源码中看到直接调用。
- D1：LLDB 调用栈证实当前运行场景确实经过。
- D2：变量/对象证据证明关键值沿此边传播。

最终报告的关键判断至少应达到 D1；涉及数据流的结论应达到 D2。

## 5. Swift 代码审计时容易漏掉的调用关系

### 闭包和回调

网络 completion、async task、Combine publisher、SwiftUI action 会让调用链不再表现为简单的 A 调 B。此时应关注闭包捕获值和回调注册点。

### 协议和依赖注入

静态类型可能是 protocol，运行时对象才决定实际实现。源码搜索只看到接口时，要在调用点动态观察对象类型。

### 属性包装器和观察机制

`@Published`、`@State`、`@AppStorage` 会隐藏读写逻辑。安全字段变化可能通过生成代码传播到 UI 或持久化。

### extension 与泛型

方法可能分散在 extension；泛型特化后会生成多个符号。断点命中多个实例不一定表示业务调用了多次。

### async/await

异步函数可能跨线程或 task 恢复，传统连续调用栈不一定保留完整业务上游。需要结合任务创建点、日志、断点命令和数据断点。

本周 Demo 刻意保持同步，目的是先建立证据方法。后续会逐步加入真实异步网络层。

## 6. 不可信静态线索

以下内容不能直接成为漏洞：

- 名称叫 `admin`、`premium` 或 `secret`。
- 二进制中出现某个 URL、token 样例或错误文案。
- 客户端存在一个返回 Bool 的权限函数。
- 请求对象里有 owner 或 role 字段。
- Debug 代码中有实验开关。

你必须继续回答：代码是否可达、值是否可控、是否进入权威决策、最终影响是什么、Release 是否存在。

## 7. 从源码生成动态假设

在启动 LLDB 前写三列表：

| 静态发现 | 动态问题 | 观察方式 |
| --- | --- | --- |
| 本地缓存可改 role/premium | 改写后 ClientPolicy 是否放行？ | evaluate 入口与返回后变量 |
| 请求复制本地 claims | 服务端收到的值是否已被污染？ | perform 的 request |
| 有两种授权模式 | 运行时到底走哪个私有函数？ | 两个授权函数断点和调用栈 |

如果观察结果与猜测不一致，要保留反证。公司更信任能够证伪自己的人。

## 8. 代码审计到逆向的迁移

| 有源码阶段 | 无源码阶段对应物 |
| --- | --- |
| 函数和类型名 | Swift/ObjC 符号、字符串、selector、交叉引用 |
| 直接调用 | 反汇编 `bl`、间接调用、动态调用栈 |
| 属性定义 | 对象布局、getter/setter、访问函数 |
| 条件判断 | 比较、条件分支、返回值和状态变化 |
| 请求模型 | 序列化函数、常量 key、网络 API 调用 |
| 单元测试 | 受控输入、差分行为、动态实验 |

本周画出的业务图就是第 3 周的分析先验，不会被丢掉。

## 9. 公司交付与工具化

源码辅助审计可以沉淀为：

- 安全敏感字段的数据流规则。
- 鉴权代码 Review 清单。
- 客户端声明与服务端权威字段对照表。
- 日志和断点证据模板。
- CI 中对危险 API 或配置的初筛规则。

但自动化通常只能提供线索。资源归属、角色语义和真实业务影响仍需人工判断。

## 10. 面试自测

- 为什么不从第一个源码文件顺序看到最后一个？
- 你如何为一个陌生业务选择首批三个断点？
- 静态调用图和动态调用栈为什么可能不一致？
- 协议、闭包和 async 会给动态分析带来什么困难？
- 一个字段没有被服务端使用，为什么可能是重要证据？
