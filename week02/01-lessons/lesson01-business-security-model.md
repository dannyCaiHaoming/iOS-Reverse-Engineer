# Lesson 01：从业务状态机到安全调用链

建议用时：90 分钟。

## 1. 公司为什么需要这项能力

真实移动安全工作很少从“这里有一个 `if`，能不能改掉”开始。公司更关心：

- 哪个资产正在被保护？
- 谁产生身份、角色、会员状态和资源归属？
- 哪个组件只是优化体验，哪个组件做最终安全决策？
- 客户端字段被修改后，服务端是否仍会独立授权？
- 一个本地现象如何转化为可复现的业务影响？

如果分析者没有先建业务模型，很容易得到两种低质量结论：

1. 看见本地 `isPremium` 可以修改，就直接报告“会员绕过”。
2. 看见服务端返回拒绝，就认为客户端没有任何安全问题。

第一种夸大影响，第二种忽略客户端的敏感数据、本地功能、反自动化和风控价值。公司的需求是准确区分边界，而不是简单说“客户端都不可信”。

## 2. 六类对象

拿到一个业务模块，先把对象分成六类：

| 类别 | 本周 Demo | 审计问题 |
| --- | --- | --- |
| 资产 | 导出报告、token、角色、会员状态 | 泄露或越权后损失是什么？ |
| 主体 | Alice、Bob、服务端会话 | 谁正在执行动作？身份由谁证明？ |
| 资源 | `requestedOwnerID` 对应的报告 | 资源归属在哪里校验？ |
| 入口 | CLI 场景，真实 App 中通常是按钮/URL/通知 | 外部输入如何进入业务链？ |
| 决策点 | ClientPolicy、ServerAuthorization | 是体验门槛还是权威授权？ |
| 消费点 | 导出结果、UI 展示、文件写入 | 决策结果最终触发了什么能力？ |

这张表应在阅读实现细节前完成。它会决定断点优先级。

## 3. 状态不是一个 Bool，而是一条生命周期

以 `isPremium` 为例，至少需要问：

```text
来源：登录响应、收据验证、本地默认值还是配置文件？
存储：内存、UserDefaults、Keychain、数据库还是服务端？
更新：登录、续费、恢复购买、切换账号、推送时谁更新？
传播：是否被复制到 ViewModel、请求头、埋点或缓存？
消费：只隐藏按钮，还是直接允许敏感动作？
失效：登出、token 过期、退款后是否清理？
权威：最终由客户端还是服务端确认？
```

面试官问“客户端会员状态怎么测”，优秀回答不是“Frida 改成 true”，而是先讲这条生命周期，再选择静态和动态观察点。

## 4. 信任边界

本周至少画出三条边界：

### 边界 A：用户输入到客户端业务对象

`requestedOwnerID` 可能来自 UI、Deep Link、WebView、缓存或服务端列表。进入 App 不代表可信。

验证重点：

- 输入能否被用户选择或篡改？
- 是否存在格式校验？
- 是否与当前登录用户绑定？
- 后续是否直接进入请求？

### 边界 B：客户端缓存到请求声明

客户端可能把 `role=analyst`、`premium=true` 放入请求。它们对调试很方便，但不能成为服务端授权依据。

验证重点：

- 请求构造是否复制本地可变字段？
- 这些字段是提示信息还是授权输入？
- 服务端是否从 token 对应的权威会话重新获取角色？

### 边界 C：认证身份到资源授权

token 有效只证明“是谁”，不自动证明“能访问哪个资源”。服务端还应校验：

- 当前主体是否拥有目标资源；
- 当前主体是否有对应动作权限；
- 状态是否有效、未过期、未撤销；
- 操作是否需要二次确认或风控。

这是 IDOR/BOLA 类问题在移动业务中的核心边界。

## 5. 三个场景分别证明什么

### `baseline`

Alice 的服务端会话为 analyst + premium，请求自己的报告。客户端放行，服务端根据权威会话和 owner 放行。

证明：正常业务链可用，后续安全测试有基线。

### `local-tamper`

Bob 的本地缓存被改成 analyst + premium，但 token 仍属于 Bob，请求 Alice 的报告。客户端放行，安全服务端根据 token 恢复 Bob 身份并拒绝 owner 不匹配。

证明：本地策略可修改；服务端没有因此失守。

未证明：真实 iOS App 一定能以同样方式修改；本周 Demo 是授权实验。也未证明本地功能完全无风险，因为离线资产或客户端敏感能力可能没有服务端兜底。

### `server-trusts-client`

Bob 本地缓存被改写，服务端只检查请求中 `claimedRole` 与 `claimedPremium`，不检查 token 对应主体是否拥有 Alice 的报告。

证明：客户端可控声明进入权威授权，导致跨用户资源访问。

真实报告必须同时记录：

- Bob 的有效身份；
- 请求目标是 Alice；
- 客户端声明来自可变本地状态；
- 服务端授权函数选择了错误信息源；
- 结果确实返回敏感资源或等价成功信号。

## 6. 攻击者模型决定评级

至少区分：

| 攻击者 | 能力 | 典型影响 |
| --- | --- | --- |
| 普通远程用户 | 改请求参数、重放自己的 token | 服务端越权、业务流程绕过 |
| 控制自己设备的用户 | 调试、Hook、修改本地文件或运行时状态 | 客户端限制绕过、本地数据访问 |
| 获得设备高权限的攻击者 | 读沙盒、进程注入、抓内存 | 凭据与隐私数据风险 |
| 恶意 SDK/组件 | App 进程内读取和调用 | 数据滥用、供应链风险 |

不要把“需要控制自己的越狱设备”写成“任意远程攻击”。也不要因为需要本机能力就自动判定无风险，关键要看资产、规模化可能性和服务端兜底。

## 7. 把业务模型转成断点计划

一个有效假设必须有观察点和证伪条件：

| 假设 | 首个观察点 | 必须继续观察 | 证伪条件 |
| --- | --- | --- | --- |
| 本地 premium 决定敏感导出 | ClientPolicy 输入与返回 | ServerAuthorization 输入与分支 | 服务端从 token 重新校验并拒绝 |
| owner 可被客户端替换 | RequestFactory 的 `requestedOwnerID` | 服务端 owner 比较 | 服务端强制使用 token 主体，不采纳客户端 owner |
| role 声明被服务端信任 | ExportRequest.claimedRole | 服务端授权数据源 | 服务端忽略声明，查询权威角色 |

本周每个断点都要能回答一个假设。没有假设的漫游式单步不计为有效训练。

## 8. 面试官如何验真

面试官可能追问：

1. 你已经把 `isPremium` 改成 true，为什么还不能定高危？
2. 服务端用了 JWT，为什么还可能有越权？
3. 客户端本地校验是否应该全部删除？
4. 请求里传 role 有问题吗？
5. 如何证明 owner 参数确实进入了授权决策？

合格回答要点：

- 本地校验可以用于体验、快速失败、离线能力和提高攻击成本，但不能是服务端授权边界。
- JWT 的签名只保证 token 声明未被篡改；资源级授权仍需独立判断，且不能信任 token 之外的客户端可控声明。
- role 字段可以作为非安全提示或遥测，但服务端授权必须使用权威来源。
- 动态证据要覆盖请求构造、服务端接收和最终分支，而不是只看 UI。

## 9. 课后自测

- 认证、授权、客户端准入三者有什么区别？
- 一个字段同时存在于 Keychain、内存 ViewModel 和请求头时，哪个值是权威值？
- 为什么最终结果相同的两个拒绝场景，也可能需要不同修复？
- 如果敏感动作完全离线，服务端无法兜底，应如何设计？
- 如何把状态生命周期转换成静态搜索点和 LLDB 观察点？
