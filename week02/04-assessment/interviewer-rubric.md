# 第 2 周面试官评分表

目的：判断候选人是真的能分析业务调用链，还是只会照着教案运行 LLDB。

## 评分总览

| 维度 | 分值 | 通过表现 |
| --- | ---: | --- |
| 业务模型与入口选择 | 15 | 能从资产/信任边界选择入口，不顺序读代码 |
| 静态调用链与数据流 | 15 | 能解释 producer/transformer/consumer 和候选图 |
| LLDB 动态证据 | 25 | 三层断点、5 节点调用链、关键变量和可复现日志 |
| 陌生/盲分析能力 | 15 | 能在时间盒内调整错误入口并形成结论 |
| 风险边界与误报排除 | 15 | 不把本地绕过等同于服务端越权 |
| 修复、复测与 SDL | 10 | 服务端权威授权、客户端改进、回归矩阵 |
| 面试表达 | 5 | 8-10 分钟结构清晰，能承认限制 |

总分 100，70 分通过。LLDB 动态证据低于 18/25 或风险边界低于 9/15，必须补考。

## Level 1：不合格

典型表现：

- 背出 `breakpoint set`、`po`、`bt`，但说不出为什么在这里断。
- 只展示本地字段改成 true。
- 不追踪 token、owner 或服务端授权。
- 直接使用教案中的函数顺序，没有自己的证据。
- 修复方案是隐藏按钮、混淆字符串或禁止调试。

面试判断：工具接触过，但不具备业务安全分析能力。

## Level 2：最低合格

典型表现：

- 能在源码指引下设置断点、看变量和调用栈。
- 能区分客户端和服务端，但证据组织较弱。
- 能提出服务端校验建议。
- 隐藏源码后需要大量提示。

面试判断：可作为初级移动安全执行人员，但 25k 竞争力不足。

## Level 3：本周目标

典型表现：

- 从业务资产和信任边界提出假设。
- 使用源码形成候选链，使用 LLDB 验证实际链。
- 对两个 tamper 场景做差分，准确说明结论边界。
- 盲分析中保留错误入口和调整过程。
- 根因落在服务端错误信任源和 owner 校验缺失。
- 修复包含正常/攻击回归用例。

面试判断：具备移动 App 业务链分析的可信基础，可以进入二进制静态分析。

## Level 4：加分表现

典型表现：

- 写出可复用 LLDB 断点命令，自动采集多场景调用栈和字段差分。
- 为授权逻辑设计属性测试或表驱动测试。
- 把主体/动作/资源模型转成 API 设计评审清单。
- 解释 Swift 优化、async 或 protocol dispatch 对证据的影响。
- 主动指出 CLI 与真实 iOS Runtime、真实 HTTP 的证据边界。

面试判断：有工程化和方法论意识，接近高级岗位需要的表达方式。

## 压力追问

讲师从以下问题随机选择：

1. 不准说函数名，你如何描述这条调用链？
2. 如果所有安全相关命名都被混淆，首批入口如何找？
3. 为什么 token 有效仍不能访问 Alice 的资源？
4. `frame variable` 看到的值是否一定是函数真正使用的值？
5. Release 优化后断点不命中，你怎么继续？
6. 本地准入完全删除会有什么产品和安全影响？
7. 你如何证明错误服务端没有做 owner 校验，而不是证据遗漏？
8. 修复后攻击请求 403，但合法请求也 403，算修好吗？
9. 这套 Demo 的哪些结论不能写入真实漏洞报告？
10. 哪一步最适合工具化，哪一步必须人工判断？

## 现场实操题

给候选人 20 分钟，仅提供已构建 Demo：

1. 列出与 export/authorize 相关的候选符号。
2. 选择两个断点并解释理由。
3. 运行任一场景，给出 5 节点调用链。
4. 指出当前 token 主体和请求 owner。
5. 说出还缺什么证据才能定业务风险。

20 分钟内只会反复单步、无法定位业务模块，说明方法尚未形成。
