# 第 2 周面试问答

## 1. 客户端本地鉴权为什么不能作为安全边界？

客户端运行在用户控制的设备上，本地状态、控制流和请求都可能被调试、Hook 或修改。客户端判断可以改善体验、减少无效请求、保护部分离线能力并提高攻击成本，但服务端资源授权必须使用服务端权威身份、权限和资源归属数据。

## 2. 你把 `isPremium` 改成 true 后看到按钮可用，能报告会员绕过吗？

只能先证明本地准入可修改。还要继续验证按钮触发的能力是否完全在本地，或者服务端是否根据 token 和权威订阅重新校验。若服务端拒绝，不能报告服务端会员权益失守；若本地仍能导出离线资产，则可评估客户端侧真实影响。

## 3. 认证和授权有什么区别？

认证确定主体是谁，例如 token 对应 Bob；授权判断该主体能否对特定资源执行特定动作，例如 Bob 能否导出 Alice 的报告。token 有效不代表可以访问任意 owner 的资源。

## 4. 请求中包含 role/premium 字段是否一定有漏洞？

不一定。它们可能用于 UI、遥测或服务端非安全提示。关键是服务端是否把客户端可控字段作为权威授权依据。需要追踪字段到最终授权消费者。

## 5. 你如何选择第一批 LLDB 断点？

先根据资产和信任边界选三个层次：敏感动作入口、本地策略判断、最终授权或敏感 API。每个断点对应一个可证伪假设，再根据调用栈扩展，不从随机函数开始连续单步。

## 6. 静态调用图和动态调用栈有什么区别？

静态图表示可能的调用关系，可能包含不可达分支，也可能因 protocol、closure、runtime dispatch 而不完整。动态调用栈证明特定输入和运行场景实际走过的路径，但只覆盖本次执行，不能自动证明其他分支不存在。

## 7. `frame variable` 和 `po` 有什么区别？

`frame variable` 主要通过调试信息读取当前 frame 的变量，副作用较小。`po` 本质上通过表达式求值打印对象，可能调用描述方法或 getter，存在执行代码、改变状态或失败的可能。证据采集优先静态读取，必要时再用表达式。

## 8. 为什么 Swift 符号断点可能命中多个位置？

编译器可能为方法主体、thunk、协议见证、闭包或泛型特化生成多个符号。应先用 `image lookup -rn` 查看完整符号和地址，再缩小正则或禁用低价值 location，并结合调用栈确认业务主体。

## 9. Debug 下能看到变量，Release 下看不到，为什么？

Release 优化可能内联函数、消除变量、改变寄存器分配、合并控制流或删除部分调试信息。分析者需要依赖寄存器、内存、函数边界和反汇编，而不能假设源码局部变量仍存在。

## 10. 条件断点在 Swift 中失败怎么办？

先无条件断住确认 frame 和变量名，再尝试字段表达式。若工具链仍不稳定，可以一次只运行一个场景，通过启动参数制造差分，或用断点命令记录后在日志中筛选。不能为了显示“会条件断点”而伪造结果。

## 11. 如何证明 owner 参数参与了授权？

要同时观察请求构造、服务端接收和最终授权分支。改变 owner 后，若服务端比较 token 主体与 owner 并导致分支变化，才能证明参与授权。仅在请求对象中看到 owner 不能证明它被正确使用。

## 12. 本周 `local-tamper` 和 `server-trusts-client` 的根本差异是什么？

两者客户端状态和请求都可相似，但安全模式从 token 获取权威主体并校验资源归属，因此拒绝；错误模式信任客户端 claims 且忽略 owner 归属，因此真正放行跨用户资源。差异位于最终授权数据源和检查逻辑。

## 13. 服务端使用 JWT 后还需要资源归属校验吗？

需要。JWT 签名可保证 token 中声明的完整性和来源，但授权仍需结合动作与目标资源。即使 token 可靠，Bob 的 token 也不能自动授权 Alice 的资源。

## 14. 本地权限判断是不是应该全部删除？

不是。它可用于 UI、快速失败、离线功能和减少请求，也能提高简单篡改成本。关键是服务端不能依赖它做权威授权，客户端也不应因为本地判断而暴露不必要敏感资产。

## 15. 你如何记录误报排除？

记录初始假设、选择入口的理由、动态观察、与假设冲突的证据、降级/排除结论和下一步。比如 local-tamper 中客户端已放行，但安全服务端基于 owner 拒绝，因此排除“已形成服务端越权”。

## 16. 修复授权问题为什么要测试合法路径？

只让攻击请求失败可以通过全拒绝实现，但会破坏业务。复测必须同时覆盖合法同用户请求、跨用户请求、无效 token、无权限用户和不存在资源，证明安全性和功能正确性。

## 17. 如何把这类问题提前放进 SDL？

在 API 设计评审明确主体、动作、资源和权威数据源；统一服务端授权中间件；Code Review 禁止信任客户端角色/会员标记；自动化测试覆盖 A 用户访问 B 用户资源；对高价值操作增加审计和异常检测。

## 18. 本周 CLI Demo 能证明你会 iOS 逆向吗？

不能单独证明。它证明我能分析 Swift 业务调用链、使用 LLDB 取证并判断客户端/服务端边界。它没有覆盖 iOS 代码签名、沙盒、ObjC Runtime、真机附加、无符号 Mach-O 和 ARM64；这些将在后续样本中补证。

## 19. 隐藏源码后，你如何避免靠记忆函数名？

重新从行为差分出发，使用更宽的业务/资产关键词做符号侦察，给候选入口评分，并用断点、调用栈和变量重新取得证据。日志保留搜索和错误入口，不能只提交记住的最终链。

## 20. 面试时如何描述本周成果而不过度包装？

可以说：我在自建 Swift 业务 Lab 中完成了源码辅助和隐藏源码两轮动态分析，使用 LLDB 还原本地策略、请求构造和服务端授权调用链，通过安全/错误模式差分证明客户端绕过与服务端越权的边界，并完成权威授权修复与回归测试。不要说发现了真实公司漏洞或已掌握复杂 iOS 无符号逆向。
