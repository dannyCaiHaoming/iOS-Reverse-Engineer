# Lesson 02：攻击面建模，先画地图再谈漏洞

## 本课目标

学完本课，你要能把一个 iOS App 拆成可审计对象，而不是看到代码就乱翻、看到工具就乱跑。

你要掌握：

- 什么是攻击面。
- 移动 App 常见攻击面有哪些。
- 如何区分资产、入口、信任边界、风险假设。
- 如何把攻击面地图写成面试材料。

## 为什么公司重视攻击面建模

安全岗位的价值不是“发现一个点”，而是系统性降低风险。公司希望你能做到：

- 上线前识别主要风险入口。
- 不漏掉高风险路径。
- 能向研发解释为什么要改。
- 能把人工经验沉淀成检查表和工具规则。

如果你只会说“我会 Frida”“我会抓包”，面试官会继续问：

> 给你一个新 App，你第一小时怎么开始？

较好的回答应该是：

> 我先做攻击面建模：看包结构、Info.plist、权限、URL Scheme、Associated Domains、ATS、本地存储、Keychain、WebView、SDK、网络接口和敏感业务流程。然后按资产和信任边界判断优先级。

## 攻击面四要素

### 1. 资产

资产是你要保护的东西。

移动 App 常见资产：

- access token
- refresh token
- 用户手机号
- 身份证号
- 定位轨迹
- 订单信息
- 会员状态
- 支付参数
- 设备标识
- 隐私授权状态
- 业务接口凭据

审计不是为了找“好玩的点”，而是为了保护资产。

### 2. 入口

入口是外部或不可信数据进入 App 的地方。

常见入口：

- URL Scheme
- Universal Link
- Push Notification payload
- Clipboard
- WebView 页面
- JSBridge
- 二维码扫描结果
- 文件导入
- 蓝牙/NFC/局域网输入
- 服务端配置下发

第 1 周先关注 URL Scheme 和 WebView。

### 3. 信任边界

信任边界是数据从一个信任域进入另一个信任域的位置。

移动 App 常见信任边界：

```text
外部 App/浏览器 -> 当前 App
Web 页面 -> Native 代码
App 本地逻辑 -> 服务端接口
用户输入 -> 业务参数
第三方 SDK -> App 数据环境
普通本地存储 -> 敏感凭据
```

面试官喜欢追问信任边界，因为它能区分你是在背漏洞，还是理解系统。

### 4. 风险假设

风险假设不是结论，而是你准备验证的问题。

例子：

```text
URL Scheme 中携带 token，可能导致敏感凭据泄露。
JSBridge 暴露 Native 能力，可能被非可信页面调用。
UserDefaults 保存 token，可能在本地分析场景泄露。
客户端会员状态可被篡改，可能绕过业务权限。
```

注意：风险假设需要验证，不能一上来就定高危。

## 第 1 周攻击面清单

### Info.plist

为什么看：

- 它暴露 App 的平台能力。
- 很多攻击面能从这里起步。

看什么：

- `CFBundleURLTypes`
- `NSAppTransportSecurity`
- 权限声明
- Associated Domains
- Background Modes
- App Groups

风险判断：

- 配置只是线索，不是最终漏洞。
- 必须结合代码和运行行为确认。

### UserDefaults

为什么看：

- 开发者容易把 token、用户信息、业务状态写进去。

风险判断：

- 非敏感偏好没问题。
- 敏感凭据、隐私数据、权限状态是风险。

### Keychain

为什么看：

- 它是凭据存储核心位置。

风险判断：

- 用了 Keychain 是加分，但还要看访问控制和服务端 token 策略。

### URL Scheme

为什么看：

- 它是外部输入进入 App 的通道。

风险判断：

- 是否传敏感数据。
- 是否触发敏感业务。
- 是否校验 host/path/query。
- 是否服务端二次确认。

### WKWebView / JSBridge

为什么看：

- 它连接 Web 和 Native。

风险判断：

- 页面来源是否可信。
- Bridge 方法是否最小化。
- 参数是否校验。
- 是否暴露 token、支付、文件、设备信息等能力。

## 如何写攻击面地图

推荐格式：

```text
攻击面：
资产：
外部输入：
信任边界：
风险假设：
验证方法：
影响判断：
修复建议：
后续是否可工具化：
```

示例：

```text
攻击面：URL Scheme
资产：token、路由参数、账号状态
外部输入：securitylab://open?token=demo-token
信任边界：外部浏览器 -> Native 路由逻辑
风险假设：外部 URL 携带 token，可能造成敏感数据泄露或业务跳转滥用
验证方法：构造不同 URL，观察 App 是否接收并处理参数
影响判断：如果只打印日志，影响较低；如果触发登录/支付/账号绑定，影响升高
修复建议：禁止 URL 传 token；白名单；参数校验；服务端鉴权
后续是否可工具化：可扫描 Info.plist 中 CFBundleURLTypes 并生成测试 URL
```

## 面试表达

不要说：

> 我会先用工具扫一下。

要说：

> 我会先建立攻击面地图，识别资产、入口和信任边界，再决定优先验证哪些风险。工具只是帮助我提高效率，不替代判断。
