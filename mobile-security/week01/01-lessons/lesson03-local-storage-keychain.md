# Lesson 03：本地存储与 Keychain，凭据安全不是一句“加密保存”

## 本课目标

本课训练你理解移动端最常见、也最容易被问深的问题：敏感数据到底应该怎么存。

你要能回答：

- UserDefaults 为什么不适合保存 token。
- Keychain 解决了什么，又没解决什么。
- 本地存储风险如何转化为业务影响。
- 审计报告中如何写验证步骤和修复建议。

## 公司为什么关心本地存储

很多 App 的真实风险不是复杂 0day，而是很朴素的工程问题：

- token 写入 UserDefaults。
- 用户隐私写入日志。
- 身份证照片缓存到普通目录。
- SQLite 明文保存敏感字段。
- 崩溃日志带上手机号和接口返回。
- 截图缓存暴露敏感页面。

这些问题对公司很现实：

- 可能造成账号接管。
- 可能触发隐私合规问题。
- 可能被安全评估、监管检查、客户审计发现。
- 修复成本不高，但需要有人能系统发现。

## iOS 常见本地存储位置

### UserDefaults

适合：

- UI 偏好
- 是否展示过引导页
- 非敏感开关
- 本地排序方式

不适合：

- token
- 密码
- refresh token
- 身份证号
- 手机号
- 会员权限状态
- 支付状态

风险原因：

- 它不是安全存储。
- 容易形成明文落盘。
- 容易被开发者误用。
- 在调试、备份、越狱、取证场景可能被读取。

### 文件和 Documents

适合：

- 用户明确生成的文件。
- 需要持久保存的业务文件。

风险点：

- 是否保存敏感数据。
- 是否被 iCloud 备份。
- 是否有合适 Data Protection。
- 是否有导出或分享路径。

### Library/Caches

适合：

- 可再生成的缓存。

风险点：

- 图片、接口响应、页面快照中可能含敏感数据。
- 缓存通常不是安全存储。

### SQLite

适合：

- 结构化本地数据。

风险点：

- 明文保存隐私字段。
- token 或业务权限状态落库。
- 日志表、埋点表、草稿表包含敏感数据。

### 日志

日志是最容易被忽略的泄露面。

风险点：

- 打印请求 header。
- 打印 token。
- 打印完整接口响应。
- 打印用户隐私字段。

面试表达：

> 我审本地存储时不会只看 UserDefaults，还会看文件、SQLite、缓存、日志、截图和备份策略。

## Keychain 讲清楚

Keychain 是 iOS 保存凭据的推荐能力，但不要把它说成绝对安全。

### Keychain 适合保存什么

- access token
- refresh token
- 用户密码或密码派生结果
- 对称密钥
- 私钥引用

### 审计 Keychain 看什么

1. 保存了什么资产。
2. 使用什么 service/account。
3. accessibility 级别是什么。
4. 是否允许迁移到新设备。
5. 是否需要设备解锁。
6. 是否需要生物识别或访问控制。
7. 是否被 App Group 共享。
8. 删除账号或退出登录时是否清理。
9. 服务端 token 是否可过期、刷新、吊销。

### 常见 accessibility 思路

第 1 周不要求背完整枚举，但要理解判断逻辑：

- 如果凭据不应迁移，倾向使用 `ThisDeviceOnly` 类策略。
- 如果设备锁定时不需要访问，倾向选择更严格的访问条件。
- 高敏感操作可考虑用户存在性或生物识别。

面试追问：

> Keychain 用 `AfterFirstUnlockThisDeviceOnly` 有什么含义？

你可以回答：

> 它表示设备第一次解锁后可访问，并且数据不迁移到其他设备。它适合某些后台访问需求，但如果业务不需要锁屏后访问，可以考虑更严格策略。具体要结合业务场景，不是固定答案。

## 本地 token 风险怎么定级

不要看到 token 就机械定高危。要问：

```text
token 是 access token 还是 refresh token？
有效期多长？
是否绑定设备？
是否能吊销？
是否需要二次校验？
是否能访问敏感资源？
泄露路径是否可行？
```

定级示例：

- 短期 access token，服务端有风控，泄露路径困难：中低。
- 长期 refresh token，明文落盘，可复用，无吊销：高。
- token 同时写入日志并上传日志平台：高。
