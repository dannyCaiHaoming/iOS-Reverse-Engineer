# Lesson 07：证据驱动的移动安全分析

## 这一课解决什么问题

公司不缺“看到 `UserDefaults` 就报高危”的人，缺的是能说明证据可靠性、业务前提和修复优先级的人。逆向题和真实审计也是同一件事：你先得到线索，再通过另一类证据验证，而不是看到一个 API 名称就宣布漏洞成立。

面试官会追问：你怎么证明这个问题真的能被触发？它影响的是本地展示，还是服务端资产？有没有正常设计会产生同样的静态线索？

## 四层结论

| 层级 | 定义 | Week 1 示例 |
| --- | --- | --- |
| 线索 | 值得检查的代码或配置 | `UserDefaults.standard.set` 出现 token 字段 |
| 已验证事实 | 可重复观察到的行为 | Lab 写入后能读回该 token |
| 风险结论 | 事实在明确前提下造成的风险 | 在已获取沙盒数据或本地备份的威胁模型下，凭据暴露面扩大 |
| 待确认事项 | 需要其他系统或角色证明 | token 是否可被服务端继续接受、是否有设备绑定或撤销机制 |

把四层混在一起是初学者最常见的问题。静态代码只能证明“可能路径存在”；运行实验能证明“本地行为发生”；服务端日志、接口响应或设计文档才能证明更高层业务影响。

## 标准证据链

```text
攻击面
  -> 风险假设
  -> 静态/配置线索
  -> 可重复运行验证
  -> 影响前提与结论边界
  -> 修复建议
  -> 复测条件
```

示例：

```text
攻击面：URL Scheme
风险假设：敏感 token 通过外部 URL 进入 App，会在日志、剪贴板、跳转链路或第三方 App 中暴露
静态线索：Info.plist 注册 securitylab；onOpenURL 读取 query 参数
运行验证：打开 securitylab://open?token=demo-token，界面显示已接收 token
结论边界：证明了客户端接受敏感 URL 参数；尚未证明真实业务 token 可被外部 App 窃取或服务端接受
修复：禁止在 URL 中传递凭据；仅接收短期一次性 code，并进行状态、来源和服务端校验
复测：传入 token 时 App 拒绝；一次性 code 过期、重放或来源不符时服务端拒绝
```

## 静态和动态证据如何配合

- 静态证据回答“路径可能在哪里”。例如 Swift 源码、`Info.plist`、Entitlements、依赖和字符串。
- 动态证据回答“路径是否真的执行”。例如操作录屏、断点、日志、受控请求和 UI 状态。
- 两者都没有时，只能记录为待分析线索。
- 两者都有，也不自动等于高危；还要看资产敏感度、攻击者能力、利用前提和服务端边界。

这正是后续逆向训练会不断复用的模式：反编译或 strings 给出线索，LLDB/Frida 给出运行事实，调用链和网络/API 行为决定最终结论。

## 可落地的修复表达

| 弱表达 | 可交付表达 |
| --- | --- |
| token 不要明文保存 | 客户端不将长期 refresh token 写入 UserDefaults；如需本地保存，使用 Keychain 并设定访问控制；服务端支持撤销、轮换和关键接口的设备/权限校验 |
| 校验 URL 参数 | Scheme 仅处理白名单路径和 schema 校验后的非敏感参数；敏感操作使用服务端签发的短期一次性 code；异常输入无副作用 |
| 限制 JSBridge | 为每个桥接方法定义允许来源、参数 schema、用户确认和服务端授权；敏感输入使用原生页面；拒绝未知 origin 和未注册方法 |

## 本课练习

为 UserDefaults、URL Scheme、JSBridge 各写一条证据日志。每条必须有一个“没有证明什么”。这句写不出来，说明结论还太快。
